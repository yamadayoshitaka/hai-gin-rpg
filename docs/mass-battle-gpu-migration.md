# 大規模戦闘 GPU 計算移行（試験実装）

## 実行経路

1. `tactics-wireframe.html` は Three.js/WebGL の実物7頭身モデル・衣装・GPUポーズ補間を維持する。
2. 100対100/1000対1000では `mass-battle-worker-client.js` から専用 Worker を起動する。
3. 通常プレイでは Worker 上の `MassBattleGridSimulation` と `CombatActionRuntime` を使用する。MP・職業魔法・蘇生・召喚獣・軍馬・状態異常・イベントは転送可能なスナップショットで画面に同期する。
4. WebGPU Compute は通常攻撃のみの試験実装として、明示的な `?army=1000&compute=gpu-basic` の場合だけ初期化する。最新版の職業スキルを再現できないため、本番プレイでは自動有効化しない。GPUでは占有マス作成、近傍敵探索、射線判定、通常攻撃、移動先競合解消、戦闘不能を並列化する。
5. 100msごとの結果を転送可能なバッファでメインスレッドに返し、既存の見た目をそのまま描画する。
6. WebGPU非対応、シェーダーコンパイル失敗、デバイス消失、無効な座標・HP、読み戻しの平均遅延増大時はCPU Workerに戻す。Worker自体が利用不可なら従来のメインスレッドAIに戻す。

## 不変条件

- 全キャラクターは同じ実物モデル、衣装、髪、武器、アニメーションシェーダーを使う。簡易モデルには切り替えない。
- 1マスに1人。橋・川・木・建物の通行判定を尊重する。
- 職業別速度・射程・攻撃間隔、全軍作戦・個別命令を維持する。
- 橋崩落後に通行可能マップとフローフィールドを更新する。
- 死亡位置・死亡モーションの補間データを失わない。

GPUの並列更新は従来CPUの兵士ID順更新とは攻撃の同時性が異なり、職業スキル・召喚獣・軍馬も未実装のため、公開ゲームのルールを保つ既定経路はCPU Workerとする。`?army=1000&compute=cpu` でも同じCPU Workerを強制できる。

## 60FPSの受け入れ条件

- Android実機で通常戦闘と1000対1000をそれぞれ最低3分間動作させる。
- WebGPU試験モードでは `window.getMassBattleStats()` の `aiExecution` が `webgpu` であることを確認する。非対応なら理由 (`gpuComputeFallbackReason`) を記録する。通常戦闘では `cpu-worker` を確認する。
- `fps` と `frameP95Ms` を確認する。安定60FPSの目安はP95フレーム時間16.67ms以下。
- `gpuFrameMs` が計測可能ならGPU描画時間も併記。非対応ブラウザでは `null`。
- `?army=1000&compute=cpu` と `?army=1000&compute=gpu-basic` の同一端末・同一描画設定で比較し、WebGPUの方が遅ければ採用しない。ゲーム仕様の互換性が得られるまでは性能が良くてもGPU試験モードを既定にしない。
- スクリーンショットでキャラクターの人体・衣装・武器・髪・エフェクトが欠落していないことを確認する。
- 戦闘中に橋を燃やし、転倒・経路変更・マス重複なしを確認する。

## 未完了・制約

- このブランチのWebGPUシェーダーはAndroid実機でのコンパイル・動作検証前である。静的契約テストのみではGPU動作や60FPSを保証できない。
- GPU計算への全面移行は未完了。現行シェーダーに職業固有技、魔法、召喚獣、軍馬、蘇生、状態異常とそのオブジェクト当たり判定を移植し、CPUと比較検証する必要がある。
- GPUの結果をWebGLへ直接共有する仕組みは使用せず、100msごとに非同期読み戻しを行う。この転送コストは端末依存。
- このGPU経路は大規模戦闘のマス・攻撃・衝突更新が対象。探索モードやラグドールなどRapierの全物理計算をGPU化したものではない。
- 並行中のワードローブ・建物・モーション改修と競合させないよう、最新版mainとの差分・回帰テスト・レビューを経て統合する。
